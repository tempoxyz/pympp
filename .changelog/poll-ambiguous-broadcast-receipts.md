Tempo charge settlement now waits for the transaction receipt when a synchronous broadcast's outcome is unknown, i.e. the `eth_sendRawTransactionSync` request times out, loses its connection after it was sent, returns an HTTP 5xx, or the node reports the transaction as already pooled. Added a `confirmation_timeout` option to `ChargeIntent` (default 30 seconds, equivalent to mppx's `confirmationTimeoutMs`) that bounds the send and receipt polling together; the send may use at most two thirds of it and its share is passed to the node as the sync timeout. Polling also stops once the transaction's `valid_before` (plus 2 seconds) has passed, after one final receipt lookup so a transaction mined before expiry is still credited. Definitive rejections fail without a receipt lookup, a recovered receipt must match the submitted transaction hash, and when no receipt arrives in time an `InternalPaymentError` is raised with the original broadcast error (or a timeout error if the send never settled) as its cause. Added `paid_retry_timeout` to `PaymentTransport`, `Client` and `request()`, applied only to the paid retry so it can wait out the server's confirmation window: when unset, the inherited read timeout is raised to at least 35 seconds; an explicit value is used exactly, and `None` inherits the timeout unchanged.
